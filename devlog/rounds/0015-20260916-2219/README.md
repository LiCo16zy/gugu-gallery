## 改动

### ① ② ⑤ 「DB 说已下载 / 磁盘上没有文件」——加了自愈

复现（用用户那份库，`data/demo` 的 19495）：

```
items 19495 → files 行在（6.44 MB、sha256 都在）
磁盘        → originals/ACG图片/Pixiv萌图/19495_….jpg 不存在（e2e-lib 里才有）
```

界面于是：卡片走缩略图 404 → 显示占位；灯箱 `/media/19495` 404 → 坏图；
「打开位置」查不到文件 → 提示「本地文件不存在」。

**这类状态本身必须能自愈**（文件被外部删掉、库被拷动、同步工具清理都会造成），于是：

- `media.rs`：`/media/<id>` 取不到文件时，顺手清掉过期的 `files` 行 → 下次查询就是「未下载」；
- 灯箱图片 `onError` 会重新拉一次详情 → 界面从"坏图"变成「这张图还没有下载到本地 + 下载此图」；
- 缩略图缺失**不**动数据库（原图还在就不该当作没下载）。

实测：先 `fileStatus: ready`，请求一次 `/media/19538`（文件已删）后变成 `fileStatus: missing, relPath: null` ✓

### ③ cookie 保存/验证的反馈

后端本来就是好的：`session.set()` 保存成功、`verify()` 会返回
`{ok:false, state:'out', message:'cookie 已过期，请重新登录'}`（区分 `in/out/unknown/error`）。
问题是**失败时只在弹窗里显示一行小字**，用户很容易当成"点了没反应"。

改动：保存失败 / 验证失败时**同时弹 toast**（`warn`），输入框内容保留可重试。

> 说明：站点 cookie 每天轮换，user 那份 `8i77…gk34` 已经过期，所以任何一次验证都会返回
> `state=out` —— 这是**正确的判定**，不是保存失败。要验证"能登录"，需要在浏览器里重新登录后
> 拿一份新的 `PHPSESSID` 再贴一次。

### 耗时分析（反馈 4）

实测数据（都是本机同一个网络）：

| 动作 | 耗时 |
| --- | --- |
| 索引 1 页（10 条，不抓详情） | **3～5 s** |
| 抓 1 个详情页（补 Pixiv ID / 画师 / 标签） | **2～5 s**（站点详情页慢） |
| 下载 738 KB 原图 | ~3～4 s（≈200 KB/s） |
| 下载 1.20 MB 原图 | ~5 s |
| 同一张 6.44 MB 原图用 curl 直连 | **11 s（578 KB/s）** |

结论：
1. **站点本身慢且不稳**：curl 单连接也只有 ~600 KB/s，且约 1/4 的请求会挂到超时或被截断，
   每次重试都要等退避 —— 这是"慢"的主要来源，不是用户网络的问题；
2. **详情补全很贵**：每条一次详情页请求，一页 10 条就是 10 次慢请求 —— 之前 Tauri 版**根本没实现**，
   所以那时反而"快"（但文件名里没有 pid、标签不全）。现在补上了，开关就是界面上的
   「下载前补全详情」，**嫌慢可以关掉**；
3. 我们的请求间隔默认 220 ms + 并发 2/3，属于保守设置（防站点压力），
   在站点正常时不是瓶颈，站点抽风时反而拖长整体时间。

顺带修掉的**功能缺口**：`enrich` 在 Rust 侧只是一个没人用的字段 —— 详情补全（Pixiv 作品号 /
画师主页 / 完整标签）整条链路缺失。现已实现，落盘文件名也重新带上 `pid…`。
