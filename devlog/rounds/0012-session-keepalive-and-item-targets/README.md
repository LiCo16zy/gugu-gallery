# 轮次 0012-session-keepalive-and-item-targets

- 时间：2026-09-16
- 应用版本：**0.6.2**
- 起点提交：`a68f1b1`
- 用户诉求：换了新 cookie、要求清掉 demo 里那 100 条 `泳装类分享` 并做抓取测试；另外「似乎网站的 cookie 每日会刷新，但我网页端依旧保持登录，如果可以我希望用户登录一次后续短时间内不再频繁登录」。

## 背景

上一轮结束时，demo 库里躺着 100 条用**旧逻辑**抓回来的 `泳装类分享` 条目（那时搜索类目标会用自己的关键词覆盖站点分类），既没有新加的标签，也和站点真实分类对不上。这一轮把它们清干净，用新 cookie 重新抓一遍做验证，并把「登录一次能用多久」这件事从根上修一修。

## 改动

### 1. 会话保活，并且跟着站点换 cookie

- **跟随轮换**：`HttpClient` 现在会读响应的 `Set-Cookie`，发现 `PHPSESSID` 变了就交给 `SessionStore.adopt()` 更新并重新加密落盘。浏览器之所以「一直保持登录」，就是因为它每次都跟着 Set-Cookie 走；应用只存一份静态值的话，站点一换就是废票。
  - 有一道必不可少的闸门：**只有本来就登录着才 adopt**。站点给每个匿名访客都会发 `PHPSESSID`，没有这道闸门的话，匿名抓一把就会把应用「变成」已登录 —— 这个坑是 uicheck 先替我踩出来的（隔离目录里凭空多出 `session.bin`，泳装分享分类莫名其妙冒了出来）。
  - 明确作废的 Set-Cookie（`max-age=0` / 1970 过期）不采纳。
- **保活**：应用开着的时候每 30 分钟探一次首页（`AppContext.startSessionKeepAlive()`），顺带把轮换的 cookie 收下来。服务端会话闲置太久会被回收，用户第二天打开就得重新登录 —— 浏览器没这个问题，只是因为用户一直在浏览。
- 探活改用一条**独立的 HttpClient**（`probe`）。之前 `verifySession()` 是借用抓取用的那条客户端、并在结束时把 cookie 清掉；如果这时候正好有抓取在跑，就会把正在进行的那批请求的登录态抹掉。

### 2. 数据模型：来源分类单独记，不再覆盖站点分类

上一轮我让搜索类目标直接把 `items.plate/word` 改成 `null / 泳装类分享`。这次真跑起来才看清代价：站点搜索页返回的详情链接仍然带着图片**原本**的分类（`/plate/ACG图片/wd/Pixiv萌图/id/...`），所以

- 那 20 条里 11 条本来就存在，被就地改成了「泳装类分享」，**Pixiv萌图 的计数直接掉了 11**；
- 再抓一次 Pixiv萌图 又会把它们改回来，标签也会被站点的标签覆盖掉 —— 同一条记录在两个分类之间来回跳。

改成正解：

- 新增 `item_targets(item_id, word)`（多对多，只增不删），记「这条是从哪个应用分类抓回来的」；
- `items.plate/word` 恢复成站点给什么就是什么；
- 侧栏分类的计数与筛选按分类类型分流：有一级分类的看 `items.word`，搜索类（泳装分享）看 `item_targets`；
- 标签照样加（用户要的），并且 `replaceTags` 会把 `item_targets` 对应的应用侧标签**留住**，不再被站点的标签重写冲掉。

schema 版本 2 → 3，新表用 `CREATE TABLE IF NOT EXISTS` 放在 `SCHEMA_SQL` 里，老库打开时自动补上，不需要重建索引。

### 3. 顺手修掉两个真 bug

- **侧栏分类点了没反应。** `patchFilters` 里「换一级分类就清掉二级分类」写成了 `if (patch.plate !== undefined) next.word = null`，而侧栏点分类时传的正是 `plate: null` + `word: 分类名` —— 于是刚设上的 word 立刻被清掉，筛选等于没生效。改成只在调用方没给 word 时才清。这个 bug 之前一直没被发现，是因为 uicheck 的断言只检查了「共 N 条」这种不管筛选与否都成立的文本。
- **选了分类，「全部」还高亮。** `isAllScope` 没把 `word` / `targetWord` 算进去。

### 4. demo 数据清理与修复

- 删掉 100 条旧 `泳装类分享` 条目、它们的 100 个原图 + 100 个缩略图（**453 MB**），并清掉空的 `originals/未分类/` 目录；删前整库备份在 `data/demo/index.db.bak-*`。
- 用新 cookie 重新抓了 3 页，那 20/30 条按详情链接把 classification 恢复正，并写入 `item_targets`。

## 遗留与说明

- **关于「站点 cookie 每日刷新」**：实测用有效 cookie 请求首页与搜索页，响应里**没有** `Set-Cookie`（也就是服务端并没有在普通请求里轮换会话号），所以「换 cookie」更像是服务端会话过期后重新签发。真正让浏览器「一直保持登录」的其实是**持续有请求**。这一轮做了两件事来逼近这个效果：跟着 Set-Cookie 走（有就换）、应用开着时每 30 分钟保活一次。**如果应用连续几天不开，服务端会话仍然可能被回收**，那时只能重新贴一次 cookie —— 站点没有提供「记住我」之类的长效凭据，应用侧拿不到更长的授权。
- 日期筛选只到月、来源分类与站点分类互斥（同时选会得到空集，代码里已经做了互斥清理）。
- 用户那份 cookie 仍然只以 DPAPI 密文存在 `%APPDATA%/gugu-gallery/session.bin`，仓库与日志里都没有明文。
